# 日常产品工作流

## 目标

把零散反馈和产品信号转化为可追踪的产品决策，并持续完成“证据 -> 洞察 -> 选择 -> 实验 -> 交付 -> 学习”的闭环。

这个 Skill 不替代团队做最终决策。它负责把信息整理到足以让负责人明确做出 Go、No-Go、继续验证或调整方向。

## 适用场景

- 每周或每两周整理用户反馈、访谈和产品数据。
- 对一批需求做主题归纳、机会判断和优先级排序。
- 把已验证的问题转成实验、PRD、用户故事或路线图调整。
- 复盘上一轮实验，决定扩大、继续、停止或转向。

如果任务只是格式校对、纯文案生成或没有产品决策目标，不要使用本 Skill。

## 必需输入

优先寻找以下材料：

- 用户反馈、访谈记录、客服工单、销售反馈或评论。
- 行为数据、漏斗、留存、分群、收入或实验数据。
- 当前目标、OKR、路线图、产品约束和团队容量。
- 已知的业务限制，例如合规、技术、渠道、成本或交付时间。

缺少关键输入时，明确写出缺口。不要编造用户数量、收入、转化率、访谈结论或市场事实。

## 证据规则

1. 区分事实、用户原话、数据结论、推断和假设。
2. 每个关键结论尽量标注来源；没有来源时标为“待验证假设”。
3. 不把单个用户的意见当成市场需求，也不把功能请求直接当成要实现的方案。
4. 先理解用户处于什么情境、试图完成什么任务，再讨论功能。
5. 如果不同来源相互冲突，保留冲突并说明下一步如何验证，不要强行合并。

## 工作流

### 1. 定义本轮要做的决策

先写清楚：

- 要决定什么：继续验证、进入方案、调整优先级、停止、上线或转向。
- 决策截止时间。
- 决策负责人。
- 本轮不讨论什么。

没有明确的决策问题时，先把任务收敛成一个具体问题。

### 2. 汇集并清洗证据

- 按用户群体、场景、痛点和触发条件整理输入。
- 将反馈转成问题主题，不要提前写成功能方案。
- 用行为数据检验反馈是否代表更广泛的用户。
- 标记样本偏差，例如只来自大客户、销售线索或单一地区。

### 3. 识别机会

优先使用机会、结果和用户任务来表达洞察，而不是功能清单。可选的分析方式包括：

- 按主题、频率、影响和战略契合度归纳反馈。
- 按行为、需求或 Jobs-to-be-Done 划分用户。
- 建立 Opportunity Solution Tree，将目标结果连接到机会、方案和实验。
- 画关键流程或用户旅程，定位高摩擦阶段。

### 4. 根据成熟度选择下一步

不要所有任务都直接进入 PRD。按证据成熟度路由：

| 当前状态 | 下一步 |
| --- | --- |
| 只有零散反馈 | 做主题归纳、用户分群和访谈 |
| 问题较清楚，但原因不清楚 | 做用户研究、数据分析和流程分析 |
| 机会清楚，但方案不确定 | 识别假设并设计低成本实验 |
| 风险假设已验证 | 写 PRD、方案范围和验收标准 |
| 已进入交付 | 拆故事、测试场景、Sprint 计划和发布说明 |
| 已上线 | 看指标、留存、实验和反馈，进入下一轮学习 |

### 5. 识别并排序假设

对关键机会列出会影响成败的假设，至少覆盖：

- 用户是否需要；
- 用户是否理解并使用；
- 技术是否可实现；
- 商业上是否可行；
- 渠道、团队和运营是否能支撑。

优先测试“影响大且不确定性高”的假设。每个实验都要有明确假设、成功标准、样本或时间边界以及停止条件。

### 6. 做优先级取舍

优先级不应只给出一张排序表。至少说明：

- 本周期最重要的结果；
- 选择这些事项的理由；
- 哪些事项明确不做；
- 资源、依赖和风险；
- 如果证据变化，什么条件会触发重排。

只有在输入数据足够时才使用 RICE、ICE 或机会评分。数据不充分时，使用“必须完成 / 应该完成 / 先学习 / 暂不处理”并明确判断依据。

### 7. 形成可交接产出

根据任务输出一种或多种产物：

- 反馈主题与分群摘要；
- 访谈提纲或访谈综合；
- 机会地图和假设清单；
- 实验计划和决策标准；
- 需求分流结果；
- 以结果为导向的路线图更新；
- PRD 或用户故事；
- 决策日志和待解决问题。

所有产出都应写明负责人、下一步动作和复查日期。

## 输出要求

默认使用中文，并包含：

1. 本轮决策问题。
2. 已知事实与来源。
3. 关键洞察。
4. 假设与未知项。
5. 推荐选择及理由。
6. 被放弃的选项。
7. 下一步实验或交付动作。

结论要区分“建议”与“已证明”。不要把推测写成事实。

## 质量门槛

- 没有明确决策问题，不进入方案和 PRD。
- 没有用户或数据证据，不声称需求已经验证。
- 没有成功标准和停止条件，不启动实验。
- 没有明确取舍，不把路线图称为战略。
- 没有负责人和复查日期，不把建议视为行动计划。
- 不要同时推进过多实验；优先减少最大的关键不确定性。

## 与 pm-skills 的映射

如果环境中安装了 `pm-skills`，优先复用以下入口，但最终仍按本 Skill 的决策和证据要求执行：

- `/analyze-feedback`：反馈聚类、情感和分群。
- `/interview`：访谈准备或访谈总结。
- `/research-users`：画像、分群和用户旅程。
- `/discover`：从创意、假设到实验的完整发现流程。
- `/triage-requests`：需求分流和优先级。
- `/transform-roadmap`：将功能清单转为结果路线图。
- `/write-prd`、`/write-stories`、`/test-scenarios`、`/sprint`：进入交付后的工作流。

不要把命令名称当成完成标准。完成标准是决策、证据、取舍和后续行动都清楚。
